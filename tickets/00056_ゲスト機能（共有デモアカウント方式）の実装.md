## 実現すること

ポートフォリオ閲覧者がアカウント登録なしで主要機能（問題生成・回答・採点・ダッシュボード閲覧）を試せる「ゲスト機能」を実装する。方式は事前のユーザー合意に基づき以下で確定する。

- **実現方式**: 固定の1つのCognitoユーザー（共有デモアカウント）へ、Top画面(S-01)の「ゲストとして始める」ボタン押下時に裏側で自動ログインさせる。Hosted UIでのメール・パスワード手入力は発生させない
- **利用範囲**: 問題生成（`POST /api/v1/question-sets`、外部API課金が発生する唯一の操作）のみクォータ制限し、それ以外（採点・ダッシュボード閲覧等）は正式ユーザーと同様に使えるようにする
- **クォータ**: IPアドレス単位で1日3回まで（デフォルト値。設定で変更可能とする）
- **データ保存**: 通常ユーザーと同じくDBに保存したうえで、約24時間後にバッチで自動削除する（S3音声ファイルを含む）。当初「完全に保存しない」案も検討したが、`question_set`/`attempt`の`user_id`が`NOT NULL`外部キーで問題生成・受験・採点の4サービスへの分岐追加が必要になり改修コストが大きいと判明したため、既存の保存経路をそのまま使える「保存＋バッチ削除」に変更した
- **導線**: Top画面(S-01)に「ゲストとして始める」ボタンを追加し、クリックでダッシュボード画面(S-07)へ自動ログイン遷移させる

### 技術方針（推奨案と理由）

1. **自動ログイン方式**: NextAuthの新規`Credentials`プロバイダー（id: `guest`）を追加し、`authorize()`からbackendの新規エンドポイント`POST /api/v1/auth/guest-token`を呼び出す。backend側はAWS SDK v2の`CognitoIdentityProviderClient`で`InitiateAuth`（`AuthFlow=USER_PASSWORD_AUTH`）を実行し、Secrets Manager経由でECSに注入された固定のゲストユーザー名・パスワードでトークンを取得して返す。frontendはそのアクセストークンを使い既存の`fetchMe`（`GET /api/v1/me`）→`jwt`/`session`コールバックの仕組みにそのまま乗せることで`session.user.id`を確定させる。Hosted UI自動送信方式（フォーム自動サブミット）はDOM構造への依存が強く壊れやすいため不採用。backend経由にすることでゲストの資格情報をVercel側に一切配布せずに済む（既存のSecrets Manager→ECSタスク定義注入パターンのみで完結する）
2. **IPクォータ**: 新規`HandlerInterceptor`（`POST /api/v1/question-sets`のみ対象）＋新規DBテーブル`guest_ip_quota`のカウント管理で実現する（Redis等の新規インフラは導入しない）。クライアントIPは`X-Forwarded-For`ヘッダーの先頭値を採用する（API Gateway HTTP API → VPC Link → ECSの構成では`request.getRemoteAddr()`はVPC LinkのENI IPを返すため使用不可。さらにfrontend→backend間はVercelの`rewrites()`経由のため、Vercelがヘッダーへ何を書き込むかは実機確認が必要）。既存の「ユーザーID単位で日次2回」制限（`QuestionSetGenerationService.checkDailyLimit`）は、共有デモアカウント（`app_user.is_guest=true`）に対してはバイパスし、IP単位の制限のみを適用する
3. **バッチ削除**: `app_user`に`is_guest`フラグを追加し（ゲスト用Cognitoクライアントの`client_id`クレームで判定して自動セット）、そのユーザーに紐づく`question_set`/`attempt`のうち作成から24時間（設定可）経過したものをSpring `@Scheduled`（既存ECS Service内、`desired_count=1`のため多重実行の心配なし）で削除する。既存スキーマには`ON DELETE CASCADE`が一切ないため、子テーブルへのカスケード削除を新規Flyway migrationで付与する。S3/ローカルの音声ファイルは`StorageService`に新設する`delete`メソッドで削除する
4. **Top→ダッシュボード遷移**: `GuestSignInButton`（`CognitoSignInButton`と同じ`isPending`制御パターン）が`signIn("guest", { callbackUrl: "/dashboard" })`を呼ぶ。`middleware.ts`の`hasAppUser`判定（`session.user.id`の有無のみ）は無変更で流用できる

### infra

- [ ] `terraform/modules/cognito`に、既存の`web` App Clientとは別の新規App Client（例: `guest`）を追加する。`generate_secret`は未指定（＝false、パブリッククライアント）、`explicit_auth_flows = ["ALLOW_USER_PASSWORD_AUTH"]`のみとし、Hosted UI/OAuthフロー関連の設定（`allowed_oauth_flows`等）は一切設定しない。既存`web`クライアントの設定・スコープには変更を加えない
- [ ] `terraform/modules/cognito`に固定のCognitoユーザー（共有デモアカウント）を作成するリソースを追加する。招待メール送信を抑止する設定（`message_action = "SUPPRESS"`等）を行う。パーマネントパスワードの設定は`aws_cognito_user_pool_user_password`リソース（pinされたAWS provider `~> 5.0`での対応バージョンを実装時に確認）を優先して使用し、非対応の場合はTerraform apply後にワンショットCLIコマンド（`aws cognito-idp admin-set-user-password --permanent`）を実行する手順をコード内コメントまたはREADMEに明記するフォールバックとする。パスワードは既存のパスワードポリシー（8文字以上・大小英字・数字必須）を満たすこと
- [ ] `module.cognito`に、新規App ClientのID（例: `guest_user_pool_client_id`）をoutputとして追加する
- [ ] 新規Secrets Manager `ielts-creater-<environment>-guest-credentials`（JSON: `username`/`password`）を、既存の`supabase_db`と同じ`valueFrom`パターンでECSタスク定義に`GUEST_COGNITO_USERNAME`/`GUEST_COGNITO_PASSWORD`として注入する
