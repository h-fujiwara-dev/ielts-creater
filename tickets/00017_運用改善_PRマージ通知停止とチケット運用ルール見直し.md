# #00017 運用改善：PRマージ通知停止・チケット運用ルール見直し

- 対象リポジトリ: root
- ステータス: 完了
- type: chore
- 関連ドキュメント: [CLAUDE.md](../CLAUDE.md#チケット運用claudeが作業する際のルール), [tickets/README.md](./README.md)

## 実現すること

GitHub運用の改善として、(1) PRマージ時にGitHub通知メールが送信されないよう4リポジトリ（root/frontend/backend/infra）のリポジトリsubscription設定を変更する。(2) チケットの実装作業は、チケットファイル自体がdevelopにマージされてから開始する運用ルールをCLAUDE.md・tickets/README.mdに明文化する（チケット定義と実装が同一の未マージブランチにまたがることで、developへの反映が遅れコンフリクトの温床になっていた問題への対処）。あわせてコンフリクト低減の観点でブランチ保護設定（Require branches to be up to date before merging）の状況も確認する。

## 受け入れ条件

- [x] 4リポジトリ（ielts-creater / -frontend / -backend / -infra）でPRマージ等のGitHub通知メールが届かないよう repository subscription を変更する（`gh api -X DELETE repos/{owner}/{repo}/subscription` で監視解除）
- [x] CLAUDE.mdの「チケット運用（Claudeが作業する際のルール）」を、チケットファイルがdevelopにマージされたことを確認してから実装ブランチを作成する二段階フローに改訂する
- [x] tickets/README.mdの運用ルールにも同様の規定を追加する
- [x] develop/mainブランチの保護設定（Require branches to be up to date before merging）が4リポジトリで有効であることを確認する

## 作業ログ

- 2026-08-10 着手。GitHub Actions・リポジトリ設定一式を調査し、PRマージ時のメール送信を行うワークフロー/設定はリポジトリ内に存在しないこと（GitHub個人アカウントの通知設定＝Watchingが原因）を確認
- 2026-08-10 4リポジトリのdevelop/mainブランチ保護設定を確認したところ、`required_status_checks.strict: true`（Require branches to be up to date before merging）が既に全リポジトリ・全ブランチで有効だったため、追加対応は不要と判断
- 2026-08-10 4リポジトリのrepository subscriptionを解除。`PUT .../subscription`に`subscribed: false`を指定してもオーナーリポジトリでは`subscribed: true`のまま反映されなかったため、`DELETE .../subscription`（Unwatch相当）で対応し、4リポジトリとも取得結果が404（購読レコードなし＝デフォルト通知のみ）になることを確認
- 2026-08-10 CLAUDE.mdとtickets/README.mdのチケット運用ルールを、チケットファイルのdevelopマージ後に実装ブランチを作成する二段階フローへ改訂。完了
